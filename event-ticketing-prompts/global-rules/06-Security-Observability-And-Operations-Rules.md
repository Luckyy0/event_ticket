# SECURITY, OBSERVABILITY, AND OPERATIONS RULES

These rules govern security requirements, observability standards, operational practices, and production hardening across the entire system.

---

## 1. Security Requirements

Every service MUST address the following security concerns:

### Authentication & Authorization
- OAuth 2.0 and OpenID Connect via Keycloak.
- PKCE for Authorization Code Flow.
- `state` parameter to prevent CSRF in OAuth flow.
- `nonce` parameter to prevent replay attacks on ID Token.

### Web Security
- CSRF protection on all state-changing BFF endpoints.
- CORS configured explicitly — no wildcard `*` in production.
- Session fixation protection (regenerate session ID after login).
- Secure Cookie attributes (HttpOnly, Secure, SameSite).

### Rate Limiting & Abuse Prevention
- Rate limiting at API Gateway level.
- Brute force protection on authentication endpoints (handled by Keycloak).
- Per-user and per-IP rate limiting for reservation endpoints during Flash Sale.

### Input Validation
- Validate all input at the adapter layer (controller) AND domain layer (business rules).
- Protect against SQL Injection (parameterized queries, JPA).
- Protect against NoSQL Injection (MongoDB query sanitization).
- Protect against SSRF (validate and whitelist external URLs).
- Protect against Mass Assignment (use explicit DTOs, never bind directly to domain entities).

### Webhook Security
- Verify webhook signatures (HMAC) on every incoming payment callback.
- Use constant-time comparison (`MessageDigest.isEqual`) to prevent timing attacks.
- Reject webhooks with timestamps older than a threshold (e.g., 15 minutes) to prevent replay attacks.
- Always return HTTP 200 to the payment gateway regardless of internal processing result.

### Header Security
- Strip spoofed identity headers at the API Gateway (e.g., `X-User-Id`, `X-Roles`).
- Do NOT trust any identity information from client-provided headers.
- Only trust identity extracted from validated JWT.

### Idempotency as Security
- Idempotency Keys prevent accidental or malicious duplicate resource creation.
- Server MUST validate that a replayed Idempotency Key with different payload is rejected (HTTP 409).

### Secret Management
- Secrets MUST NOT be hardcoded in source code.
- Secrets MUST NOT be committed to Git.
- Local development: use `.env.example` as a template, never commit actual `.env`.
- Production: use Kubernetes Secrets, HashiCorp Vault, or cloud-native secret managers.
- Rotate secrets periodically (Keycloak client secrets, HMAC keys, database passwords).

## 2. Sensitive Data Logging Prohibition

Logs MUST NOT contain any of the following:

```
Access Token
Refresh Token
ID Token
Authorization Code
Password
Session Cookie value
HMAC secret
Payment card numbers
CVV
Bank account details
Personal identification numbers
Webhook raw signatures
```

When logging request/response for debugging, mask or redact sensitive fields:
```java
log.info("Payment webhook received: provider={}, transactionId={}, amount={}",
    provider, transactionId, amount);
// Do NOT log: signature, raw body containing card data, tokens
```

## 3. Observability — Mandatory per Service

Every service MUST implement:

### Structured Logging
- Use SLF4J + Logback.
- JSON format in production.
- Include contextual fields: `correlationId`, `traceId`, `spanId`, `userId`, `service`.
- Use MDC (Mapped Diagnostic Context) to propagate correlation IDs across threads.

### Correlation ID
- Generated at BFF or Gateway.
- Propagated through HTTP headers (`X-Correlation-Id`).
- Included in every log statement.
- Included in every Kafka event.
- Enables tracing a single user action across all services.

### Trace ID
- Generated by the distributed tracing framework (OpenTelemetry).
- Propagated automatically via instrumentation.

### Health Checks
| Endpoint | Purpose |
|---|---|
| `/actuator/health/liveness` | Is the process alive? (Kubernetes liveness probe) |
| `/actuator/health/readiness` | Is the service ready to accept traffic? (Kubernetes readiness probe) |
| `/actuator/health` | Composite health including dependencies |

Readiness check MUST verify:
- Database connection is available.
- Redis connection is available (if used).
- Kafka producer can connect (if used).

Liveness check MUST be lightweight — do NOT check external dependencies in liveness.

- `inventory.reservation.total` (counter, tags: result=success|rejected|expired)
- `inventory.reservation.duration` (timer)

- `order.created.total` (counter)

- `payment.webhook.received.total` (counter, tags: gateway, result)
- `payment.webhook.duplicate.total` (counter)
- `payment.webhook.processing.duration` (timer)
- `payment.refund.total` (counter, tags: result)

## 5. Distributed Tracing

Technology: OpenTelemetry (preferred) or Micrometer Tracing.

Backend: Tempo or Jaeger.

Requirements:
- Automatic instrumentation for Spring MVC, WebClient, JPA, Kafka, Redis.
- Custom spans for critical business operations (reservation, payment processing).
- Trace context propagation across HTTP calls and Kafka messages.
- Sampling strategy: 100% in development/staging, configurable in production.

- Grafana dashboards for log exploration by correlationId, traceId, service, level.

## 7. Alerting

### Critical Alerts (Page immediately)

```
Inventory available quantity < 0 (over-selling detected)
Payment webhook signature verification failures > 10 in 5 minutes
Outbox events stuck in PENDING > 15 minutes
Dead Letter Topic message count > 0
Order state inconsistency detected by reconciliation
Payment amount mismatch between webhook and database
Database connection pool exhausted
Redis connection failures
Kafka consumer lag > threshold for > 5 minutes
```

### Warning Alerts (Investigate within hours)

```
Webhook processing latency p99 > 500ms
Reservation expiration job execution time > 30 seconds
Idempotency key collision rate spike
Error rate > 1% on any endpoint
JVM memory usage > 80%
HikariCP pending connections > 0 sustained
```

## 8. Audit Logging

Audit logs MUST be recorded for:

- User login and logout.
- Order creation, cancellation, refund.
- Payment state transitions.
- Ticket issuance and cancellation.
- Admin actions (user management, manual refund, reconciliation trigger).
- Inventory manual adjustments (if any).
- Security events (failed authentication, authorization denial, rate limit hit).

Audit log fields:
```json
{
  "timestamp": "2026-08-03T13:00:00Z",
  "actor": "user-id or system",
  "action": "ORDER_CREATED",
  "resourceType": "order",
  "resourceId": "order-uuid",
  "correlationId": "correlation-uuid",
  "details": {},
  "outcome": "SUCCESS or FAILURE",
  "ipAddress": "masked or hashed",
  "userAgent": "..."
}
```

Audit fields (createdBy, createdAt, updatedBy, updatedAt) MUST be designed into database schemas from the beginning, even if the audit-service is deployed later.

## 10. Production Hardening

### Graceful Shutdown
- Every service MUST handle SIGTERM gracefully.
- Complete in-flight HTTP requests.
- Commit or rollback active database transactions.
- Stop Kafka consumers and wait for in-progress messages to complete.
- Close Redis connections cleanly.
- Spring Boot `server.shutdown=graceful` with configurable timeout.

### Database Operations
- Flyway migrations MUST be backward compatible (no destructive changes without a migration plan).
- Connection pool sizing must be documented and justified.
- Slow query logging enabled.
- Statement timeout configured to prevent runaway queries.

### Kafka Operations
- Consumer group ID must be unique per service.
- Consumer must handle rebalancing gracefully.
- Producer must use idempotent mode (`enable.idempotence=true`).
- Acknowledgment: `acks=all` for critical topics.

### Backup and Recovery
- PostgreSQL: automated daily backups with point-in-time recovery capability.
- MongoDB: automated backups.
- Redis: RDB snapshots + AOF (if persistence is needed for session data).
- Keycloak: realm export/import for disaster recovery.
- Kafka: topic retention policy configured per topic based on business needs.

### Disaster Recovery Scenarios
- Database crash and restore from backup — reconciliation to detect gaps.
- Redis crash — rebuild from PostgreSQL (Redis is not source of truth).
- Kafka unavailable — Outbox accumulates, relay catches up on recovery.
- Keycloak unavailable — existing valid JWTs continue to work until expiration; new logins fail.
- Single service crash — other services continue via eventual consistency; reconciliation detects gaps.

## 11. Kubernetes Operations (Advanced Stage)

### Resource Configuration
- Deployment, Service, Ingress per service.
- ConfigMap for non-secret configuration.
- Secret for sensitive configuration.
- Resource requests and limits (CPU, memory) per container.
- Liveness, Readiness, and Startup probes.

### Scaling
- Horizontal Pod Autoscaler (HPA) based on CPU, memory, or custom metrics.
- Pod Disruption Budget (PDB) to ensure availability during rolling updates.
- Rolling update strategy with `maxSurge` and `maxUnavailable`.

### Deployment Safety
- Flyway migrations run as init containers or during startup (not as a separate job unless necessary).
- Kafka consumer shutdown is graceful before pod termination.
- Redis connections are closed cleanly on SIGTERM.
- Keycloak deployed separately with its own lifecycle.
